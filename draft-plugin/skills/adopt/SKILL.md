# 既存プロジェクトへの導入(adopt)

## 目的

DRAFT外で作られた(またはdocsが失われた)既存プロジェクトに、変更サイクル(/draft:feature)を回すための前提(ソース層ドキュメントと検出点)を用意する。

新規構築のPhase 0〜5は踏み直さない。コードから読み取れる「現状」を逆生成し、コードから読み取れない「意図」をヒアリングで補い、ユーザー検証を経て正とする。

## 前提(入力)

- 既存のソースコード(gitリポジトリ推奨)
- docs/ にDRAFTのソース層(`design-spec.md`、`02-01_system-design-doc.md`)が無いこと。既にある場合はこのスキルの対象外なので、/draft:guide で現在地を診断する
- 既存のREADMEや設計メモがあれば逆生成の材料として活用する。**ただし現状の正はコード。** 既存docsとコードが食い違ったらコードに従い、古い記述をそのまま転記しない(古い理想の混入は、捏造と同じ穴を別経路で開ける)

## 進め方

### Step 1: コードベースの調査

リポジトリを調査し、結果を**中間ファイル `docs/_adopt-survey.md`** に書き出す(後工程に渡すのは常にファイル。このファイルは導入作業の足場であり、Step 6で削除する):

- 技術スタック(フレームワーク・ORM・DB・認証・ホスティング・CI/CD)
- 画面/ルートの一覧、APIエンドポイントの一覧、データモデル(スキーマ定義から。定義と実DBの乖離が疑われる場合(未適用マイグレーション等)は未確認として記録する)
- コマンド体系(package.json / Makefile / CI設定から)と、ブランチ運用の実態(git履歴から)
- モノレポで複数アプリがある場合は、一覧をアプリ別に整理する(生成するドキュメントは後述のとおり1本にまとめる)
- **未確認事項の一覧**(surveyの独立した節にする)。コードから確定できない事項は推測で埋めず、**事実1件ごと**(画面・エンドポイント・テーブル・判断の単位)に記す。章単位・ドキュメント単位でまとめない。粒度が粗いとStep 5のレビューとStep 6の検証が機能しなくなる

**規模が大きい場合は分担する:** 画面が20を超える、またはエンドポイントが50を超える規模では、サブエージェント(Agentツール)に機能領域ごとの調査を分担させ、各結果を `_adopt-survey.md` に集約する。調査でコンテキストを使い切ったら、Step 2以降は新しいセッションで再開する(surveyファイルが受け渡しになる。以降の各Stepも、重くなったらsurveyと生成済みドキュメントを受け渡しにセッションを分けてよい)。

### Step 2: 意図のヒアリング

コードには「何があるか」しか無い。「なぜ作ったか・誰のためか・何をスコープ外にしているか・何を計測したいか」をAskUserQuestionで聞く(選択式・1テーマずつ。2〜4往復で十分)。PRDの材料はここでしか得られない。

Step 1の未確認一覧のうちユーザーが即答できそうな事項(意図・方針の類)も、ここで質問の種にする。固定カテゴリの一般論だけで終わらせない。

質問では、画面・エンドポイント・テーブルを名前と役割で指し、surveyの番号やIDだけで指さない。コードから読み取れたことを質問文に添え、ユーザーがコードやsurveyを開かずに答えられるようにする(README原典の原則)。Step 6で未確認事項を提示するときも同じ。

### Step 3: ソース層の現状版ドラフトを生成

事実の所有権マップ(README原典)に従い、docs/ に生成する。モノレポでも design-spec / System Design Doc は各1本にまとめ、アプリ別の章で分ける(所有権を分散させない):

| ドキュメント | 内容 |
|-------------|------|
| `design-spec.md` | 画面一覧・目的・レイアウト・認証要否・コアフロー・対応言語(i18n方針。未確認なら未確認と明記)。現状の記述。データモデル章は作らない(所有はSystem Design Doc) |
| `02-01_system-design-doc.md` | スタック(ADRは「現状の選定と、わかる範囲の理由」として最小限)・ルーティング表・API設計・データモデル(ER図+実スキーマ)・セキュリティ(権限マトリクスは実装から起こす) |
| `01_prd.md` | Step 2のヒアリングから。KPIが未定なら「未定」と書く(捏造しない) |
| `03_dev-setup.md` | 実在するコマンドと、実態のブランチ運用(理想でなく現状を書く。宣言と実態を初日から食い違わせない) |
| `docs/README.md` | 簡易インデックス: ドキュメント一覧(実在するものだけ)+ 裁量規定で省略した成果物の記録(何をなぜ省いたか1行ずつ) |

- 各ドキュメントで、コード由来の事実とヒアリング由来の事実を区別し、確認できていない箇所は「未確認: 〜」と**事実1件ごと**に明記する(surveyの未確認一覧とも同期させる)
- `screen_flow.mermaid` は画面遷移が複雑な場合に生成する(コア導線だけでもよい)
- 04(デプロイ手順)・05(運用Runbook)は、デプロイ・運用が実在するプロジェクトでのみ実態から起こす(README原典 Phase 3の裁量規定)。省略したら `docs/README.md` に根拠を1行残す

### Step 4: CLAUDE.md と検出点の配置

/draft:prep の要領で配置する。**prompts.md は作らない**。あれは新規構築の足場であり、導入済みプロジェクトの変更は /draft:feature が担う:

1. このスキルのディレクトリにある `CLAUDE.template.md` の構成に従って `CLAUDE.md` を生成する。**テンプレートの項目は実態に合わせて削除・修正する**。具体的には、Docs節の `docs/claude-code-prompts.md` への言及は削除し、生成していないドキュメント(`02-02` / `04` / `05` 等)への言及も削る。実在しないファイルを参照するCLAUDE.mdを作らない。末尾のDRAFT版数スタンプも記録する(/draft:prep と同じ要領)。既存の CLAUDE.md / AGENTS.md がある場合は上書き前にユーザーへ確認する(マージも選択肢に)
2. このスキルのディレクトリにある `doc-lint.template.sh` を `scripts/doc-lint.sh` にコピーして実行権限を付け、`.githooks/pre-commit` を作成して(内容は2行: `#!/usr/bin/env sh` と `exec scripts/doc-lint.sh --staged`)実行権限を付け、`git config core.hooksPath .githooks` を実行する。Makefileが無いプロジェクトでは、CLAUDE.md の Commands 節を**全行**実態に合わせる: `make doc-lint` は直接実行(`scripts/doc-lint.sh --docs`)に、他の `make *` はプロジェクトの実コマンドに置換するか、実コマンドをラップする最小限のMakefileを作って参照を保つ。未定義の `make` 参照を残すと、配置した doc-lint 自身が初回の `--docs` で検出する
3. `ln -s CLAUDE.md AGENTS.md` で `AGENTS.md` リンクを作る(既に実体の AGENTS.md がある場合は上書きせずユーザーに確認)

### Step 5: 独立レビュー

サブエージェント(Agentツール)で、生成の経緯を知らないレビュアーに生成ドキュメント一式を渡して検証させる。**観点ごとにレビュアーを分け、1メッセージ内で同時に起動する:**

- **docs-code整合**(渡すもの: 生成ドキュメント一式、`_adopt-survey.md`): 記述が実装の現状と一致しているか。存在しない画面・API・テーブルを書いていないか、主要な実装の見落としがないか。網羅の確認はsurveyとの突き合わせを主とし、コードの探索は疑義のある箇所の確認に限る(範囲を切らないとリポジトリ全体の探索が始まり長時間化する)
- **所有権**(渡すもの: 生成ドキュメント一式): 同じ事実が複数ドキュメントに転記されていないか。データモデルがSystem Design Docのみにあるか
- **未確認の網羅**(渡すもの: 生成ドキュメント一式、surveyの未確認一覧): 「未確認」とすべき箇所が断定で書かれていないか。逆生成の最大のリスクは、コードから読めない意図の捏造

指摘は重大度付きで返させ、修正は自分で行う。**セルフレビューへ勝手に落とさない。** 独立レビューを起動できない場合(Agentツールが無い、使用に許可が必要など)は、理由を添えて選択肢をユーザーに示して選ばせる: (1) Agentツールを使う許可をもらう (2) 新しいセッションに生成ドキュメントとsurveyだけを渡してレビューする (3) 独立性が落ちることを承知でセルフレビューで進む。取った経路は次の報告に1行明記する。

### Step 6: ユーザー検証と昇格

生成ドキュメントの要点と「未確認」の一覧をユーザーに提示し、確認・修正してもらう。

- 軽微な修正はその場で反映する
- **主要な見落としや大きな誤りが見つかったら、修正で繕わずStep 1(該当領域の再調査)に戻る。** 修正が大きければ、Step 5のレビューを該当観点だけ再実行する
- 未確認が解消された時点でソース層として確定し、`_adopt-survey.md` を削除する(足場を残すと第2の正になる)。以後は通常の規律(所有権マップ・実装後更新・変更サイクル)に従う

## 成果物

| 成果物 | 場所 |
|--------|------|
| ソース層の現状版(design-spec / System Design Doc / PRD / dev-setup。検証済み) | `docs/` |
| `docs/README.md`(簡易インデックス+省略記録) | `docs/` |
| `CLAUDE.md` | リポジトリルート |
| `scripts/doc-lint.sh` + `.githooks/pre-commit` | リポジトリ |

`_adopt-survey.md` は昇格完了時に削除済みであること(残っていたら未完了)。

## 次のフェーズ

/draft:feature で変更サイクルを開始する(FDD要否判定から)。`concept.md` / `brainstorm-notes.md` は作らない。UIモックも描かない(見た目はすでに実装にある)。アーカイブ層は空から始まり、以後の経緯はFDDとgit履歴が蓄積する。

## 注意

- **現状を写す。理想を書かない。** dev-setupのブランチ戦略は実態(main直運用ならmain直)を書く。理想への移行は導入後の変更サイクルで行う。宣言と実態の乖離を初日から作ると、実運用で最も形骸化しやすい箇所を自分で仕込むことになる
- **意図を捏造しない。** KPI・スコープ外・設計判断の理由は、ヒアリングで得られなければ「未確認」「未定」と書く。もっともらしい推測で埋めると、以後の壁打ちがその捏造を正として設計する
- **未確認は事実1件ごとに書く。** 章単位の「詳細は未確認」に丸めると、レビューも検証も素通りする
- **フェーズを遡らない。** concept / brainstorm / prompts.md は新規構築の足場であり、動いているプロダクトには不要
- **データモデル章をdesign-specに作らない。** 所有はSystem Design Doc(README原典の移管規定)
- **導入だけで完了とする。** 調査中に見つけたバグや改善はこのスキルでは直さない。導入完了後に /draft:feature で変更サイクルに乗せる(1サイクル1目的)
