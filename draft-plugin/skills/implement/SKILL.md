# Phase 5: 実装(ステップ実行)

## 目的

Phase 4で生成したステップ別プロンプト集(`docs/claude-code-prompts.md`)のうち、**1ステップだけ**を実装し、動作確認済みの状態で完了させる。全ステップを順に消化していくことで、動くアプリケーションを完成させる。

DRAFTの原則「**1ステップ = 1チャット**」を厳守する(`docs/claude-code-prompts.md` が同一チャットでの実行を明記しているステップ群のみ例外)。1セッションで複数ステップを続けて実行すると、コンテキストが肥大し、自動要約による詳細の損失・注意の希釈で品質が低下する。

## 前提(入力)

以下がリポジトリに存在することを確認する:

- `CLAUDE.md`(リポジトリルート)— プロジェクトコンテキスト
- `docs/claude-code-prompts.md` — ステップ別プロンプト集
- `docs/` 配下のPhase 2〜3成果物(design-spec.md、02-01_system-design-doc.md など)

`docs/claude-code-prompts.md` が見つからない場合はリポジトリルートも探す。それでも無ければ、**このフェーズを実行してはいけない**。Phase 4(実装準備)が未完了である旨を伝え、先に `/draft:prep` でCLAUDE.mdとプロンプト集を生成するよう案内して終了する(`CLAUDE.md` が無い場合も同様に `/draft:prep` へ案内する)。フェーズを飛ばしてその場でアプリを作り始めることは絶対にしない。

## 進め方

### 0. 実行モードの判定

起動時の引数に `loop` が含まれていれば**無人ループモード**で実行する(駆動スクリプトが `claude -p '/draft:implement loop'` で1ステップにつき1セッションを起こしている)。このモードにはユーザーへ問い合わせる経路が無いため、末尾の「無人ループモード」節の差分を適用したうえで以下を実行する。引数が無ければ既定の対話実行で、以下をそのまま実行する。

### 1. ステップ一覧の把握

`docs/claude-code-prompts.md` をReadし、以下を整理する:

- 全ステップの一覧(番号・内容・ゴール)
- 各ステップの「動作確認可能なゴール」(「〜が動く状態」)
- 各ステップが参照を指示しているdocsファイル
- 各ステップの「まだやらないこと」(スコープ外)
- 各ステップの `Status:` 行(空欄=未着手 / `done YYYY-MM-DD` / `blocked YYYY-MM-DD` + 直後1行の理由)

### 2. 実行ステップの決定(ユーザーに確認)

プロジェクトの現状から**未完了の最初のステップ**を推定する。推定材料:

- リポジトリのファイル構成(package.json / スキーマ定義 / APIルート / 認証コード / UIコンポーネント / terraform / テストの有無)
- `git log --oneline` の履歴
- `docs/claude-code-prompts.md` 内の `Status:` 行(旧形式 — チェックボックス `[x]` や `<!-- DONE -->` コメント — の完了マークがあればそれも)

推定結果を踏まえ、**AskUserQuestionツールで選択式に確認する**:

- 第一候補: 推定した「次のステップ」(推定理由を添える)
- その他の選択肢: 前後のステップ、または「別のステップを指定する」

ユーザーが最初から「Step Nをやって」と指定している場合は確認を省略してよいが、そのステップより前に未完了のステップがありそうな場合は依存関係の観点から一言指摘する(最終判断はユーザーに従う)。

**例外:** `docs/claude-code-prompts.md` がチャット分割の目安として同一チャットでの実行を明記しているステップ群(例:「Step 1〜2は1チャットにまとめてもOK」)は、1セッションでまとめて実行してよい。それ以外は1ステップ = 1セッションを厳守する。

### 3. 実装(選ばれた1ステップのみ)

1. ステップのプロンプトが参照を指示しているdocsファイルを**先にRead**する。必要な情報だけ読み、docs全部を読み込まない
2. プロンプトの指示に従って実装する。技術スタック・設計方針は `CLAUDE.md` と `docs/02-01_system-design-doc.md` に従い、**このフェーズで技術スタックを変更しない**
3. 「まだやらないこと」に挙げられた項目には手を出さない(スコープクリープ防止)。ただしこの縛りは未着手の機能に対するもので、作った実装に見つかった欠陥には適用されない(欠陥の扱いは§4)
4. **残作業を残さない。** ステップのゴールを満たしていない状態は、名前が何であれ未完了である。TODO/FIXMEコメント、固定値やモックを返す仮実装、握りつぶした例外、通していない経路、完了報告に付ける「今後の課題」節は、すべて先送りの言い換えでしかない。禁止しているのは形ではなく先送りそのものなので、TODOを避けて別の形で残すのは同じ違反。書きたくなったら、プロンプトか設計に曖昧さがあるサインなので、その場でユーザーに確認して解消してから実装する(必要なら該当docsにも反映する)
5. **設計の不備を実装で回避しない。** 「設計ドキュメントの記述では要件が満たせない・記述同士が矛盾している・必要な決定が欠けている」と気づいたら、実装側の回避策で辻褄を合わせて進まない。手を止め、不備の内容・影響・直し方をユーザーに提示し、合意の上でソースDoc(`docs/design-spec.md` / `docs/02-01_system-design-doc.md`)を直してから、直った設計を入力に実装を再開する。設計の不備ではない細部の調整(命名、レスポンス形状の微修正)は実装を進めてよく、§6-1で反映すれば足りる
6. **スコープを縮めるのはユーザーの決定。** 進めてみてゴールまでが遠いと判断したら分割してよいが、自分で決めない。縮める範囲と理由をユーザーに提示して合意を取り、残りを `docs/claude-code-prompts.md` に新しいステップとして追記してから、前半をこのセッションの完了とする。口頭の「残りは次回」で終わらせない
7. **合意を求めること自体を完了の代わりにしない。** 合意が要るのは**ユーザーのスコープを縮めるとき**だけである。自分の実装が作った穴、自分やレビュアーが見つけた欠陥を塞ぐのに合意は要らない — それは縮小ではなく完了条件なので、「これも直しますか」と聞かずにその場で閉じる。許可を求める形は配慮に見えるぶん、先送りの隠れ蓑になりやすい
8. **残すときは、閉じられない理由を名指しする。** やむを得ず残す項目には、「後で」ではなく**何がブロックしているか**(ユーザーの決定が要る/認証情報や外部リソースが無い/別ステップの成果物に依存する)を、先送りするその時点で事実として添える。後から理由を組み立てると、指摘に整合するよう基準が後付けで作られ、検証できないものが基準の顔をする
9. **コメントはコードから読み取れないことだけを書く。** 処理の言い換え(`// ユーザーを取得する` の直後に `getUser()`)は書かない — 情報を持たないうえコード変更に追随せず嘘になる。書くのは「なぜこの実装なのか」「不変条件」「外部制約」「呼び出し側の契約」。密度と体裁は周囲の既存コードと `CLAUDE.md` のCode Styleに合わせる

**エラーが出たら場当たり的に直さない。** エラーメッセージを読み、根本原因(依存関係、設定、設計との不整合など)を特定し、原因と修正方針を提示してから修正する。設計に関わる修正(スキーマ変更、設計との不整合の解消など)はユーザーの合意を得てから行う。症状だけ抑える暫定パッチを重ねると、後のステップでエラーが積み上がって修正困難になる。

### 4. 独立レビュー(必須)

動作確認の前に、生成したコードをレビューする。サブエージェント(Agentツール)で、実装の経緯を知らないレビュアーを起動し、このステップのdiffと参照したdocsだけを渡して検証させる(実装中の会話や判断の経緯は渡さない — 書いた本人の思い込みを引き継がずに欠陥を見つけるため)。

**観点ごとにレビュアーを分け、1メッセージ内で同時に起動する。** 1体に全観点を載せると直列に見ていくため待ち時間が積み上がるが、同時起動なら待ち時間は最も遅い1本で済む。各レビュアーには担当する観点と、その判断に要るものだけを渡す:

- **実装の欠陥**(渡すもの: diff) — 認証ガード: protected routesに認可チェックが漏れなく入っているか。バリデーション: APIの入力検証が全エンドポイントにあるか。シークレット: APIキーやパスワードがハードコードされていないか(.env参照になっているか)。依存パッケージ: 新規に追加されたパッケージが実在し、名前が正当か(タイポスクワッティング・幻覚パッケージの混入)
- **先送りと残骸**(渡すもの: diff、このステップのゴール) — ゴールに対して未完のまま残っている箇所がないか。TODO/FIXMEコメント、固定値やモックを返す仮実装、握りつぶした例外、空実装のハンドラなど、形を問わず「後で直す前提のコード」を探させる。実ファイルを追加したディレクトリに `.gitkeep` が残っていないか(残っていたら削除する)。コードの言い換えでしかないコメントが残っていないか(判定基準は「そのコメントを消して情報が失われるか」— 失われないなら削除する。Whyを説明しているコメントは残す)
- **docs整合**(渡すもの: diff、参照したdocs) — 実装が参照したdocsの記述から逸脱していないか。逸脱がある場合、それは合意済みの設計変更としてソースDocに反映されているか

**渡した範囲の外を探しに行かせない。** diffとdocsは実体で渡し(長ければファイルに書き出してパスを渡す)、範囲外のファイルを開くのは担当観点の判断に必要なときだけに限る(例: 認可漏れの判定でミドルウェアの既存実装を確認する)。範囲を切らないと、レビュアーはリポジトリ全体の探索から始めて1回の実行が長くなる。

指摘は重大度付きで返させ、修正は自分で行う。重大な指摘は修正後に再確認する(再確認は指摘のあった箇所に限り、全観点を起動し直さない)。

**指摘に「スコープ外」という行き先は無い。** 指摘は「欠陥か(仕様・意図からの乖離、壊れているもの)、改善提案か(仕様の外)」で判定する。欠陥は、このステップのスコープ外に見えても聞かずにその場で閉じる。閉じられない理由(ユーザーの決定が要る/認証情報や外部リソースが無い/別ステップの成果物に依存する)を名指しできるものだけが、合意のうえ `docs/claude-code-prompts.md` に書き出す対象になる(§6)。改善提案は残作業ではないので、記録せず完了報告で言及するに留める。構築中の残作業の行き先は `docs/claude-code-prompts.md` ただ一つ — /draft:feature(イテレーション)は全ステップ完了後の入口であり、構築中のステップから残作業を送る先ではない。

**独立レビューを起動できない場合(Agentツールが無い、セッションの制約で使用に許可が必要など)、セルフレビューへ勝手に落とさない。** 理由を添えて選択肢をユーザーに示し、選ばせる:

1. Agentツールを使う許可をもらう(経緯を知らないレビュアーを起動する)
2. 新しいセッションに成果物(diffと参照したdocs)だけを渡してレビューする
3. 独立性が落ちることを承知でセルフレビューで進む(その場合も上の観点を全て確認する)

取った経路は完了報告に1行で明記する(例: `独立レビュー: 未実施(セルフのみ。ユーザー承諾済み)`)。品質基準を下げる決定はユーザーのものであり、単独で下さない。

### 5. 動作確認(必須)

ステップの種類に応じて、以下の表の該当する確認を**必ず実行してから**完了を宣言する:

| ステップの種類 | 確認方法 |
|------|----------|
| 骨格(初期化・開発環境) | `make dev` で両方のサーバーが起動する |
| DBスキーマ + シード | `make db-push` + `make db-seed` + `make db-studio` でデータが見える |
| バックエンドAPI | `curl` で各エンドポイントが200を返す |
| 認証 | ブラウザでOAuthログインが通る |
| UI | ブラウザでコアフローが一通り動く |
| インフラ | `terraform plan` がエラーなく通る |
| テスト | `make test` が全パス |

(コマンド名はプロジェクトの `CLAUDE.md` / `docs/03_dev-setup.md` に定義されたものを優先する。Makefileが無い既存プロジェクトでは、そのプロジェクトの流儀のコマンドに従う。)

UI・APIの確認では、正常系に加えて設計仕様書が定義する異常系の最低ライン(不正入力のエラー形式・未認証拒否・空状態の表示)も確認する。テスト資産が導入済みの状態(Step 9完了後、または `make test` が定義済みのプロジェクト)では、ステップ種別に関わらず既存スイートの全パスも確認に含める。

ブラウザ操作が必要な確認(OAuthログイン、コアフロー)は、自動で確認できない場合はサーバーを起動した上でユーザーに手動確認を依頼し、結果を聞いてから完了とする。

確認が失敗したら、根本原因を特定して修正し、再度確認する。**動作確認をパスするまで完了を宣言しない。**

### 6. 完了処理

**完了を宣言する前に、残作業がゼロであることを確認する。** ステップのゴールが動作確認で満たされ、TODO/FIXME・仮実装・通していない経路が1つも残っていない状態だけが完了である。残っているものは、まずこの場で解消する。`docs/claude-code-prompts.md` のステップとして書き出してよいのは、**この場では閉じられない理由を名指しできるもの**(ユーザーの決定が要る/認証情報や外部リソースが無い/別ステップの成果物に依存する)だけで、その理由をステップに書き添え、ユーザーの合意を取る。理由を名指しできないなら、それは閉じられるということなので閉じる。完了報告に「今後の課題」節を作って積み残さない。残す先はリポジトリ内のファイルだけ — ファイルに書かれていないものは残っておらず、消えている(完了報告やチャットで行き先に言及しても記録にはならない)。

1. **ソースDocの同期**: このステップの実装がdocsの記述から逸脱した場合(合意して行った設計変更・仕様調整)、変わった事実の所有ドキュメントを現在の実装に合わせて更新する(画面・UX・認証要否 → `docs/design-spec.md`、API・データモデル・ルーティング → `docs/02-01_system-design-doc.md`、コマンド・環境構築 → `docs/03_dev-setup.md`)。逸脱がなければ何もしない。更新は「現在の状態」の書き換えとして行い、更新履歴・編集ログは残さない
2. 実装内容の要約(作成・変更したファイル、動作確認の結果、**独立レビューの経路**)をユーザーに報告する。レビューをサブエージェント以外の経路で行った場合は、その事実を報告に含める(ツール実行の前置きに書いただけでは報告したことにならない)
3. `docs/claude-code-prompts.md` の該当ステップの `Status:` 行に `done YYYY-MM-DD` を記録する(行が無い古い prompts.md では見出し直下に追加する)。ゴールに届かないまま終える場合は `blocked YYYY-MM-DD` を記し、**直後の1行に閉じられない理由を名指しで書く**(ユーザーの決定が要る/認証情報や外部リソースが無い/別ステップの成果物に依存する)。空欄のままにしない — 「未着手」と「試して閉じられなかった」が区別できなくなり、次のセッションと無人ループが同じステップを繰り返す。**閉じられない部分を新しいステップに切り出したときは、切り出し先の `Status:` にも `blocked YYYY-MM-DD` と理由を書く。**空欄で挿入しない — 空欄は「未着手」の意味なので、次の反復がそれを普通の作業として掴み、ユーザーの決定が要ると自分で宣言した部分をループが代わりに決めてしまう。駆動スクリプトが読むのは `Status:` 行だけで、ステップ本文に書いた理由は届かない。空欄で書き出してよいのは、大きすぎるステップを分割した残り(実装でき、後の反復が回収できるもの)だけである。旧形式のマークが残っているファイルでは、この機会に全Stepのマークを `Status:` 行へ読み替えて統一する(新旧混在のまま増やさない)。次回セッションでの進捗推定に使うため、口頭報告だけでなくファイルに残す
4. **Skillツールで /draft:commit を呼び出してコミットする。** 自分でメッセージを組み立てて `git commit` しない — コミットの規約(履歴の全文確認・言語判定・トレーラーの扱い・ユーザーへの提示と合意)は /draft:commit の中にあり、呼ばなければ1つも適用されない。渡す文脈は対象ステップ名と、独立レビューの実施経路(コミット本文の検証記述に載せる)

## 無人ループモード

駆動スクリプトが1ステップにつき1回、新しいセッションとしてこのスキルを起動している状態(§0で判定済み)。ユーザーへ問い合わせる経路が無いので、対話実行から**次の表の点だけ**を差し替える。表に挙がっていない規律は一切変わらない — 残作業ゼロ、独立レビュー必須、動作確認必須、コミットは /draft:commit 経由。

| 節 | 対話実行 | 無人ループ |
|----|--------------|-----------|
| §2 実行ステップの決定 | AskUserQuestionで確認する | `Status:` が空欄の最初のステップを選ぶ。確認しない |
| §3-5 設計の不備 | ユーザーに提示して合意を得る | 自律的にソース層を直して実装を続け、判断を記録する(下記) |
| §3-6 スコープの分割 | 縮める範囲の合意を得る | 自律的に分割し、残りを `docs/claude-code-prompts.md` に新しいステップとして書き出す(実装できる残りは `Status:` 空欄、人の判断が要る部分は `blocked` + 理由。§6-3) |
| §4 独立レビューが起動できない | 選択肢を示して選ばせる | 止める(`blocked`)。セルフレビューに落とさない |
| §5 ブラウザでの動作確認 | ユーザーに手動確認を依頼する | 自動で確認できる手段(ヘッドレスE2E等)をこのステップの成果物として用意し、それで確認する。用意できない外部要因があるときだけ止める(`blocked`) |
| §6-4 コミット | メッセージを提示して合意を得る | 提示せずコミットする(/draft:commit は呼ぶ。合意の手順だけを飛ばす) |

`claude -p` はフルセッションなのでAgentツールを持ち、独立レビューは通常どおり起動できる(駆動スクリプトが走行前に確認する)。§4の行は、走行中に起動できなくなった例外の扱いである。

分割はループでは成果物を縮めない。残りは新しいステップとしてファイルに載り、後の反復で回収される。対話実行で合意を求めていたのは、口頭の「残りは次回」で消えるのを止めるためだった。回収が保証されるなら、この歯止めは要らない。独立レビューの起動不可はこれと違い、自律判断の対象外にする。ここでの選択肢は「品質基準を下げて進む」しか無い。品質基準を下げる決定はユーザーのものであり、ループはそれを代行しない。

### 自律判断の記録(必須)

上の表で自律的に下した判断は、**コミット本文に**書く。書くのは3つ:

1. 何を選んだか
2. なぜそれを選んだか
3. 他にどの選択肢があって、なぜ採らなかったか

/draft:commit の本文規約(「なぜ変えたか・何を検討して採らなかったか・どこまで検証したか」)がそのまま記録先になる。**専用のログファイルは作らない** — 構築中の経緯の所有権はgitにあり、二重管理を作らない。

**チャットへの出力は記録ではない。** 無人ループの標準出力は走行後に残らない。人が事後監査するのはコミット履歴で、本文に書かなかった判断は、下していないのと同じ扱いになる。事前の承認を飛ばせるのは、事後に読めるからである。書かなければ、飛ばした分がそのまま抜ける。

自律判断を1つも下していない反復では、この記録は書かない(書くことが無いのに節を作らない)。

### 止まる条件

次のいずれかに当たったら、`Status:` に `blocked YYYY-MM-DD` と理由を記して(§6-3)このセッションを終える。駆動スクリプトはこれを読んでループを止める。READMEが定める3状態のうち「保留」がこれにあたる:

- 独立レビューを起動できない
- 動作確認を自動化する手段を用意できない外部要因がある(実アカウント・課金・外部サービスの認証情報が要る等)
- 設計の不備が、ソース層のどの直し方を選んでも仕様の意図を満たせない(直し方の選択ではなく、仕様そのものの決定が要る)

**「時間がかかりそう」「難しそう」は理由にならない。** `blocked` は人の判断が要ることの表明であって、難易度の表明ではない。難しいだけの作業を `blocked` に逃がすと、ループは先送りの新しい出口になる。

### ループの起動

対話セッションで「ループで回して」と求められたら、**セットアップはこのスキルが行う**。手順を読ませてユーザーに代わりにやらせない。判断が要るのは権限と起動方法の2つだけで、残りは機械作業である。

1. `docs/claude-code-prompts.md` を読み、未着手のステップ数を数える。`blocked` のステップが残っていれば、ループは1歩も進まないので先に理由を提示して片付ける
2. このスキルのディレクトリの `run-loop.sh` を、プロジェクトの `scripts/draft-loop.sh` へコピーする(既にあれば内容を比べ、古ければ上書きする)
3. **権限をユーザーに確認する。** 無人実行なので、実装に要るツールが問い合わせ無しで通る状態が要る。既定の `acceptEdits` はファイル編集しか通さないため、多くのプロジェクトではプロジェクトの `.claude/settings.json` に許可リストを作るか、`DRAFT_LOOP_PERMISSION_MODE=bypassPermissions` を指定することになる。どこまで許すかはユーザーの決定なので、代わりに決めない
4. **起動方法をユーザーに確認する。** 1で数えた未着手ステップ数を判断材料として添える(下表)。数だけで自動的に決めない — 席を外すかどうかは数からはわからない
5. 背景実行を選ばれたら起動し、終了時に結果を報告する。ターミナルを選ばれたらコマンドを渡す
6. どちらでも、走行後に積まれたコミットを読むよう伝える(`git log` の本文が事後監査の対象)

| 起動方法 | 向くとき | 制約 |
|---------|---------|------|
| このセッションから背景実行 | 残りが少なく、終わるまで見ていられる | プロセスがセッションに紐づく。窓を閉じると途中のステップで止まる |
| ユーザーのターミナル | 残りが多い、離席する | セッションから独立して走り切る |

利用上限に当たっても走行は止まらない。駆動スクリプトはリセットまで待って同じステップを再開し、その反復を停滞として数えない。待ちを挟むと走行は数時間に伸びうるので、残りが多いときはユーザーのターミナルで回す。

**前景(背景でないBash)で回さない。** Bashツールの上限は10分で、複数ステップの走行は完走しない。背景実行なら子セッションの出力は親のコンテキストに入らず、完走もできる。

背景実行がセッションの終了で止まると、そのステップは `Status:` が空欄のまま作業ツリーだけが変更された状態で残る。次の走行は同じステップを最初からやり直すので、**再開の前に作業ツリーを確認する**。中途半端な変更が残っていれば、捨てるか内容を見て整理してから再実行する。

前提の点検(プロンプト集の有無・独立レビューが起動できるか)は駆動スクリプトが走行前に行う。ここで先回りして確認しない — 二重に持つと片方が古くなる。1で読むのは起動方法を決めるための残ステップ数であって、点検の代わりではない。

駆動スクリプトは Claude Code の `claude` CLI を子プロセスとして起動する。他のクライアント(Codex・Cursor等)からこのスキルを読んでいる場合、無人ループを使うには `claude` が別途必要になる — 起動コマンドをそのクライアントのものに読み替えるのではなく、`claude` を入れるか対話実行で進む。

## 次のフェーズ

- **未完了のステップが残っている場合**: 次のステップは**新しいセッションで** `/draft:implement` を再度実行するよう案内する(残りを人手を挟まず消化したい場合は無人ループも案内する。§無人ループモード)。CLAUDE.mdは新しいセッションでも自動で読まれ、作成したファイルはディスクに残っているため、引き継ぎ説明は不要である。ユーザーが同一セッションでの続行を強く希望する場合のみ従うが、コンテキスト劣化による品質低下のリスクを一度は伝えること
- **全ステップ完了の場合**: フル構築は完了。以降の変更は `/draft:feature`(イテレーション: FDD要否判定 → 壁打ち → Feature Design Doc → 実装。振る舞いが変わらない変更はFDD不要で直接実装 + /draft:commit)で行うと案内する

## 注意

- **全ステップを1つのセッションで実行しない。** コンテキストの肥大で品質が低下する（自動要約による詳細の損失・注意の希釈）。1ステップ完了ごとにセッションを切るのがDRAFTの設計
- **動作確認せずに次のステップへ進まない。** エラーが積み上がると原因の切り分けが困難になる
- **生成されたコードは必ず独立レビューにかける。** 書いた本人によるセルフレビューは思い込みを引き継ぐ。特にセキュリティ(認証ガード、バリデーション)。AIが生成したコードの認可漏れは典型的な事故ポイント
- **独立レビューを黙って省略・代替しない。** 起動できないときはユーザーに選択肢を示し、取った経路を完了報告に明記する。セルフレビューだけで「レビュー済み」と読める報告をすると、検証されていないコードが検証済みとして次のステップの土台になる
- **先送りしない。完了とは残作業がゼロの状態。** TODOコメント・仮実装・通していない経路・完了報告の「今後の課題」節は、形が違うだけの同じ問題である。1つの形を塞いでも別の形で残せば違反は残る。判定は形の列挙ではなく記録先で行う — リポジトリ内のファイルに書かれていないものは残っておらず、消えている。`.gitkeep` の残骸も含め、レビューで掃除する
- **欠陥を「スコープ外」で落とさない。** 「まだやらないこと」が縛るのは未着手の機能。欠陥の行き先は「その場で閉じる」か「理由を名指しして合意のうえ `docs/claude-code-prompts.md`」の二つだけで、/draft:feature は全ステップ完了後の入口であり構築中の行き先ではない
- **設計の不備は設計に戻して直す。** 実装で辻褄を合わせて後からdocsを合わせると、設計判断がコードに埋もれ、レビューされないまま確定する。不備に気づいたら止めてユーザーと合意し、ソースDocを直してから実装を再開する
- **スコープを黙って縮めない。** 分割は有効な手だが、縮める判断はユーザーのもの。合意を取り、残りをファイルに書き出してから完了とする
- **合意を求めることを完了の代わりにしない。** 「これも直しますか」と聞けば未完が未完でなくなるわけではない。合意が要るのはユーザーのスコープを縮めるときだけで、自分が作った穴・自分で見つけた欠陥は聞かずに閉じる。許可を求める形は配慮に見えるぶん、先送りの隠れ蓑になりやすい
- **残す理由は事後に組み立てない。** 先送りするその時点でブロッカーを名指しする。指摘を受けてから理由を作ると、指摘に整合するよう基準が後付けされ、検証できないものが基準の顔をする
- **技術スタックを実装フェーズで変更しない。** ドキュメント全体の書き直しになる。変更が本当に必要なら、いったん停止してPhase 3のドキュメントから直すようユーザーと合意する
- **場当たり的なエラー修正をしない。** 根本原因を特定し、原因と修正方針を提示してから直す。症状だけ抑えるパッチは原因の解決を後ろに送る先送りの一形態。設計に関わる修正はユーザーと合意してから
- **コメントで実況中継しない。** AIは行ごとに処理を言い換えるコメントを書きがちだが、情報ゼロで読解コストだけ取り、コード変更に追随せず嘘になる。書くのはWhyであってWhatではない
- **コミットは /draft:commit を呼び出して行う。** 手元の要約で済ませて自分でコミットすると、履歴の全文確認・言語判定・トレーラーの扱いが揃って抜け落ちる
- **後工程に渡すのは常にファイル。** 進捗・決定事項はセッション内の合意で終わらせず、`docs/claude-code-prompts.md` 等に書き残す
- **無人ループを「聞かなくていいモード」と読み替えない。** 差し替わるのは差分表の6点だけで、それ以外の規律は対話実行と同一である。ループは問い合わせ経路が無いという制約への適応であって、品質基準の緩和ではない。表に無い場面で勝手に判断を増やすと、ループは既存の規律すべてに対する逃げ道になる
- **`blocked` は人の判断が要ることの表明であって、難易度の表明ではない。** 難しいだけ・時間がかかるだけの作業をここへ逃がすと、無人ループは先送りの新しい出口になる。理由に書けるのは「何がブロックしているか」という事実だけ
- **自律判断はコミット本文に残す。** 無人ループの標準出力は走行後に残らないため、本文に書かなかった判断は検証できない。事後監査が成立しないなら、事前合意を省いた分がそのまま欠落になる
- **ループのセットアップを案内で終わらせない。** スクリプトの配置と残ステップ数の確認は判断を含まない機械作業なので、スキルが実行する。手順を書いて読ませるのは、機械作業をユーザーに代行させているだけである。判断が要るのは権限と起動方法の2つだけで、そこだけを聞く
