# Phase 2: 設計仕様書

## 目的

Phase 1（壁打ち）で合意した内容を「設計仕様書」として書き出す。
ゴールは、開発者（ユーザー自身を含む）が読んでそのまま画面が作れるレベルの具体性。
この仕様書はPhase 3（開発ドキュメント）以降のすべての工程が参照する情報源になる。

**大原則: 後工程に渡すのは常にファイル。** 口頭（チャット内）の合意ではなくMarkdownに書き出す。

## 前提（入力）

1. `docs/brainstorm-notes.md`（Phase 1の壁打ちメモ）と `docs/concept.md`（Phase 0のコンセプト）をReadする
   - 同一セッションでPhase 1の壁打ち直後なら、その文脈をそのまま使ってよい。ただしその場合もファイルは必ずReadし、チャット内の記憶とファイルの内容がズレていないか確認する
2. `docs/brainstorm-notes.md` が存在しない場合はフェーズを飛ばさない。壁打ちが未実施であることをユーザーに伝え、先に `/draft:brainstorm` を実行するよう案内する（設計仕様書なしでPhase 3に進むと、API設計とUI設計が噛み合わなくなる）
3. このスキルのディレクトリにある `design-spec.template.md` と `screen_flow.template.mermaid` をReadする。これが成果物の構成の基準になる
4. `docs/design-spec.md` が既にあれば、途中のドラフトとして読み、どこまで合意済みかを確かめて続きから進む。Step 4で拡張機能を入れるために再起動した場合は、Step 4から再開する。書き出してあるドラフトを、最初から作り直して上書きしない

## 進め方

### Step 1: 材料の確認

入力ファイルを読み、以下がPhase 1で合意済みかを確認する:

- 画面一覧（名称 + 目的 + 簡易説明）
- 画面遷移の全体像
- ロール定義
- コアフロー（最も重要なユーザー体験の流れ）

欠けている項目があれば、仕様書を書き始める前にAskUserQuestionで確認して埋める。
このとき壁打ちの流儀に従う: **選択式で聞き返す、1テーマずつ、完璧を求めず先に進める。**

### Step 2: 設計仕様書のドラフト作成

`design-spec.template.md` の9章構成に従って設計仕様書を書く:

1. プロダクト概要（コンセプト、方針、UI設計原則）
2. ユーザーロールとフロー
3. 画面一覧
4. デザインシステム（レイアウトパターン + ビジュアルデザイン方針）
5. 画面遷移（別紙 `screen_flow.mermaid` への参照）
6. コア画面詳細仕様
7. データモデル
8. デモデータ仕様
9. 今後の検討事項

このとき、以下の7項目は必ず含める（READMEのPhase 2「設計仕様書に含めること」に対応）:

1. プロダクト概要（コンセプト、方針（対応言語含む）、UI設計原則）
2. ユーザーロールとフロー
3. 画面一覧（全画面の名称・目的・レイアウト・認証要否）
4. コア画面の詳細仕様（各ステップで何が表示され、何が操作できるか。エラー・空・ローディング状態も含む）
5. ビジュアルデザイン方針（トーン&ムード、カラーの方向性、タイポグラフィの方向性、ライト/ダークモード対応、情報密度）
6. データモデル（ER図 + 各テーブルのカラム定義）
7. 画面遷移図（Mermaid形式で**別ファイル**）

執筆時の指針:

- **仕様書は長くていい。** 網羅性より簡潔さを優先しない。Phase 3以降でAIが参照するための情報源なので、判断根拠や具体的な表示内容まで書き込む
- 画面一覧には全画面について「名称・目的・レイアウトパターン・認証要否」を表で記載する
- デザインシステムのレイアウトは「画面の目的別にレイアウトパターンを定義 → 全画面にマッピング」の順で体系化する（例: 左右分割＝参照と操作を同時に行う画面、中央集中＝1つの対象に注目させる画面、カードグリッド＝比較・選択する画面）
- ビジュアルデザイン方針（4.4）は方向性まで（トーン&ムード、カラーの方向性、タイポグラフィの方向性、ライト/ダークモード対応、情報密度）。HEXコード等の具体値は設計仕様書に書かない。Phase 3で `docs/06_design-tokens.json`（デザイントークン）として確定し、以降の値の正はそちらが持つ（Step 4のモックで描いた値は、Phase 3でモックからトークンに写す）。ライト/ダークモードの要否だけはこの段階で決める（後付けは高くつく）
- コア画面の詳細仕様にはASCIIレイアウト図を含め、各ステップ（状態）ごとに「何が表示され、何が操作できるか」を書く
- コア画面はエラー・空（データ0件）・ローディングの各状態で何が表示されるかも仕様化する（正常系だけの仕様書だと、実装時に状態設計が抜ける）
- プロダクト方針には対応言語を明記する（i18nの要否はここで決める。不要なら「日本語のみ」と書く。後付けは高くつく）
- データモデルは論理設計レベルでよい（Phase 3でORMスキーマコードに変換する前提）が、エンティティ・関係性・カラム定義はここで確定させる。データモデルの所有権はPhase 3でSystem Design Docへ章ごと移り、design-spec側の章は削除されて参照1行に置き換わる（移管は /draft:playbook が行う）。以降のスキーマ変更はSystem Design Docのみを更新する

### Step 3: コア画面の深掘り

コアフローに関わる画面や、仕様が曖昧な画面は、書きっぱなしにせずユーザーと対話して詰める。
AskUserQuestionを使い、画面ごとに以下の5観点で確認する:

- ユーザーが画面を開いたとき何が見えるか
- 操作可能なアクションは何か
- 各アクション後の状態遷移は何か
- エラー時・データが空のとき何が見えるか
- レイアウト（左右分割？中央集中？グリッド？）

レイアウトが画面ごとにバラバラになりそうな場合は、
「画面の目的別に最適なレイアウトパターンを定義し、全画面にマッピングする」体系化を提案して4章を固める。
ビジュアルデザイン方針（4.4）もこの深掘りで確認する（トーン、カラーの方向性、モード対応など。壁打ちの流儀で1テーマずつ、選択式で）。

深掘りも壁打ちの流儀で行う: 選択肢を提示して選んでもらう、1画面（1テーマ）ずつ、ユーザーが「それで良い」と言ったら先に進む。全画面を深掘りする必要はなく、コア画面と曖昧な画面に絞る。

質問文では画面を名前と目的で指す。画面一覧の番号や遷移図のノード名（`A1` など）は括弧で添えるだけにして、それだけで指さない。ユーザーが仕様書を開かずに答えられる材料を質問文に入れる（README原典の原則）。

### Step 4: モックで見た目を合意する（UIのあるプロダクトのみ）

UIの無いプロダクト（CLI、APIだけのサービスなど）はこのStepを飛ばす。

言葉だけの合意では、ユーザーは見た目を判断する材料を持てない。言葉で決めきれなかった見た目は、Phase 5で実装のエージェントが自分で決めてしまう。設計仕様書を確定する前に、描いて合意する。

描き始める前に、ここまでのドラフトを `docs/design-spec.md` に書き出してから、/draft:equip-extensions を呼び、モックを描くのに使う拡張機能を選ぶ（何も入れないと決めてもよい）。入れた拡張機能を使えるようにするには、読み込み直しや再起動が要ることがある。書き出しておけば、再起動してもStep 3までの合意が消えない。この時点の選定はモックを描くためだけのもので、プロジェクトとして採用するわけではない。

1. **描く範囲を決める。** コア画面と、レイアウトパターン（4.1）ごとの代表の1画面だけを描く。全画面は描かない（描く量が画面の数だけ増える）。対応する画面幅によってレイアウトが変わるなら、変わる幅ごとに描く。ライト/ダークの両モードに対応するなら、最低1画面は両方を描く
2. **方向性が決まっていなければ、先に比べる。** ビジュアルデザイン方針（4.4）が固まっていなければ、代表の1画面で2〜3案を描いて見比べてもらい、方向性を決めてから残りを描く
3. **HTMLで描き、PNGに撮る。** 1画面を1つのHTMLにし、スタイルはファイルの中に書いて、それだけで表示できるようにする。データはデモデータ仕様（8章）に沿った現実的なものを入れる（空のモックでは密度を判断できない）。`docs/mocks/` にHTMLを置き、ブラウザで撮ったPNGを同じ名前で並べる。スクリーンショットを撮る手段（Playwright、ブラウザを操作するツールなど）は、その場で使えるものを使う。撮れないときは、理由を添えてユーザーに選択肢を示す（撮る手段を用意する／ユーザーがHTMLを開いて撮る）
4. **1画面ずつ合意する。** ユーザーにPNGを開いて見てもらい、何を見てほしいか（配置、密度、何を目立たせているか）を添えて確認する。直しが出たら描き直して撮り直す。ユーザーが「それで良い」と言ったら次の画面へ進む
5. **合意した判断を設計仕様書に書き写す。** モックに写っている判断（レイアウトパターンの定義と画面への割り当て、情報密度、何を目立たせるか、ビジュアルデザイン方針）を、該当する章の文章にする。色や余白の値はここでは書かない（Phase 3でモックからトークンに写す）。モックは合意した時点の記録（アーカイブ層）で、Phase 5を終えると参照されなくなる。文章に写さなかった判断は、そこで失われる
6. **描いて見つかった食い違いは、ここで解く。** 描くと、文章のままでは気づかないルール同士の食い違い（パネルを開くと本文が狭くなりすぎる、など）が見つかる。設計仕様書を直してから先に進む

### Step 5: 画面遷移図の作成

`screen_flow.template.mermaid` の形式に従い、画面遷移図をMermaidの `graph TD` で書く。

- 共通画面（LP、認証）→ ロール別の画面群、という構造でロールごとにセクションを分ける
- 設計仕様書の「3. 画面一覧」に載っている全画面が図に登場することを確認する
- **仕様書本文には埋め込まず、必ず別ファイルにする**

### Step 6: 書き出しと独立レビュー、最終確認

1. `docs/design-spec.md` と `docs/screen_flow.mermaid` に書き出す（`docs/` がなければ作成する）
2. **独立レビューを行う。** サブエージェント（Agentツール）で、作成の経緯を知らないレビュアーを起動し、書き出したファイルだけを渡して検証させる（壁打ちの会話や判断理由は渡さない。先入観なく矛盾を見つけるため）。**観点ごとにレビュアーを分け、1メッセージ内で同時に起動する**（1体に全観点を載せると直列に見ていくため待ち時間が積み上がるが、同時起動なら待ち時間は最も遅い1本で済む）:
   - 内部整合（渡すもの: 2ファイル）: 画面一覧・画面遷移図・データモデル・コア画面詳細仕様が互いに矛盾していないか（図に登場しない画面、仕様のないテーブル参照など）
   - 抜け（渡すもの: 2ファイル）: コア画面のエラー・空・ローディング状態、対応言語（i18n方針）、ビジュアルデザイン方針（ライト/ダークモード対応含む）が明記されているか
   - 写し漏れ（UIモックがある場合。渡すもの: `docs/design-spec.md` と `docs/mocks/` のPNG）: モックに写っている判断（配置、密度、何を目立たせるか、状態の見せ方）のうち、設計仕様書に書かれていないものはないか。モックと設計仕様書が食い違っていないか
   **渡したファイルの外を探しに行かせない。** 範囲を切らないと、レビュアーはリポジトリ全体の探索から始めて1回の実行が長くなる。
   指摘は重大度付きで返させ、修正は自分で行う。重大な指摘は修正後に再確認する（再確認は指摘のあった箇所に限り、全観点を起動し直さない）。
   **セルフレビューへ勝手に落とさない。** 独立レビューを起動できない場合（Agentツールが無い、セッションの制約で使用に許可が必要など）は、理由を添えて選択肢をユーザーに示して選ばせる: (1) Agentツールを使う許可をもらう (2) 新しいセッションに書き出したファイル（モックがあればそれも）だけを渡してレビューする (3) 独立性が落ちることを承知でセルフレビューで進む。取った経路は次の最終確認で1行明記する（例: `独立レビュー: 未実施（セルフのみ。ユーザー承諾済み）`）。品質基準を下げる決定はユーザーのものであり、単独で下さない
3. 書き出した内容の要点（画面数、ロール数、テーブル数、コア画面、モックを描いた画面）をユーザーに提示し、特に**データモデル**について最終確認を取る
4. 修正指示があればファイルを更新する

## 成果物

| ファイル | 内容 |
|----------|------|
| `docs/design-spec.md` | プロダクト設計の全体像（9章構成） |
| `docs/screen_flow.mermaid` | 画面遷移図（Mermaid形式、別ファイル） |
| `docs/mocks/` | UIモック（画面ごとのHTMLと、同じ名前のPNG）。UIのあるプロダクトのみ。合意した時点の記録で、Phase 3とPhase 5の入力になる |

## 次のフェーズ

設計仕様書が固まったら、Phase 3（開発ドキュメント）へ進む。

- `/draft:playbook` を案内する
- 新しいセッションでの開始を推奨する（コンテキストを軽く保つため）。ただしユーザーが同一セッションで続けたい場合はそのまま続行してよい。成果物はすべて `docs/` のファイルとして残っているので、どちらでも品質は変わらない

## 注意

- **仕様書は「長くていい」。** Phase 3以降でAIが参照するための情報源。短くまとめようとして情報を削らない
- **データモデルはこの段階で固める。** 後から変えるとAPI設計から全部やり直しになる。曖昧なまま先に進めず、Step 6でユーザーの確認を必ず取る
- **design-specは画面・UXの所有ドキュメント。** 画面の存在・目的・レイアウト・認証要否・UXの振る舞いはこのファイルが正であり、Phase 3以降もそれらが変わるたびに更新される「生きたソース」になる（例外はデータモデル章で、Phase 3でSystem Design Docへ章ごと移り、design-spec側は参照に置き換わる）
- **Mermaid図は別ファイルにする。** 仕様書本文に埋め込むと後工程のAIが図を読み飛ばすことがある
- **モックは描き直さない記録。** 合意した時点で確定し、Phase 3（トークンの値）とPhase 5（実装の手本）の入力にだけ使う。後で見た目の判断が変わったら、モックではなく設計仕様書を直す。食い違ったら設計仕様書が正で、設計仕様書に書かれていない見た目はモックに合わせる
- **フェーズを飛ばさない。** 壁打ち（Phase 1）の合意なしに仕様書を書くと方向性がブレる。逆に、設計仕様書なしでPhase 3（開発ドキュメント）を作るとAPI設計とUI設計が噛み合わない
- 技術スタックの選定はこのフェーズの仕事ではない（Phase 3で確定させる）。ユーザーが技術の話を始めたら、要望をメモとして「9. 今後の検討事項」に残しつつ、画面とデータの設計に集中させる
- 深掘り対話では完璧を求めない。ユーザーが決めきれない項目は妥当なデフォルトを提案して先に進み、「9. 今後の検討事項」に記録する
